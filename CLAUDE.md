# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ApexCycling: a web app for track cycling training data. It ingests raw session
data from `my.sqorz.com` transponders (Strava/Garmin planned later, not yet
built), normalizes it into per-lap/per-segment training facts, and serves an
SPA with session detail + progression charts. Auth, club/athlete data model,
sqorz ingestion (manual + background polling), normalization, and charts are
built. Club-admin roster management and a coach dashboard are the last open
v1 milestone (M4b — see `BACKLOG.md`).

## Commands

Backend (from `backend/`, with `.venv` activated):
```bash
pip install -e ".[dev]"
python -m pytest                    # full suite (in-memory SQLite, no services needed)
python -m pytest tests/test_foo.py::test_name   # single test
ruff check .
alembic upgrade head                 # requires a real Postgres DATABASE_URL — migrations are Postgres-specific
uvicorn app.main:app --reload
python -m app.ingestion.runner       # background sqorz poller (APScheduler), optional for local dev
python -m app.db.seed                # seed a demo club/coach/athlete (password devpassword123 for all)
```

Frontend (from `frontend/`):
```bash
npm install
npm run dev
npm run build      # tsc -b && vite build — this is what CI runs, so a type error fails it
npm run lint       # oxlint
npm test           # vitest (jsdom + Testing Library, setup in src/test/setup.ts)
```

Production (single VPS, see deploy.md; scripts in `scripts/`):
```bash
sudo scripts/server-setup.sh                      # once, bare Ubuntu 24.04 (Docker, ufw, fail2ban, swap)
scripts/init-env.sh <domain> <email>              # writes .env.prod with fresh secrets
scripts/deploy.sh [--no-pull|--rollback]          # build, back up, up --wait, health check, auto-rollback
scripts/compose.sh <compose args>                 # docker compose against the deployed image tag
sudo scripts/restore.sh latest                    # replaces ALL data from the newest backup
scripts/compose.sh exec backend python -m app.auth.cli create-admin <email> "<name>"
```

Browser smoke tests (from `e2e/`, Playwright; any base URL, deletes the account it signs up):
```bash
npm install && npx playwright install chromium   # once
E2E_BASE_URL=https://apex-cycling.net E2E_EDGE=1 npm test   # E2E_EDGE=1 also asserts Caddy's headers; default target is the dev stack on :5173
```

Full stack via Docker (recommended for manual/e2e testing):
```bash
cp .env.example .env
docker compose up --build   # db (Postgres 16), backend (:8000), worker, frontend (:5173)
```

CI (`.github/workflows/ci.yml`, on push to `master` and PRs) runs backend `ruff` + `pytest`, a Postgres job doing `alembic upgrade head` → `alembic check` (fails if models drifted from migrations) → `downgrade base` → `upgrade head`, and frontend `lint` + `test` + `build`. Every new migration must keep that round-trip and `alembic check` clean.

The backend `.venv` console scripts have stale shebangs from the Track Trainer rename — use `.venv/bin/python -m alembic` / `-m pytest` rather than `.venv/bin/alembic`.

For a SQLite dev DB (skipping Postgres/Alembic entirely), see `backend/tests/conftest.py::db_session` for the pattern: `create_async_engine("sqlite+aiosqlite:///:memory:")` + `Base.metadata.create_all`, then override the `get_db` FastAPI dependency.

## Backend architecture

**Ops & prod** (`docker-compose.prod.yml`, `docker/Caddyfile`, `app/ops/`, `app/admin/`, `app/core/logging.py`): Caddy is the only published service (80/443, automatic Let's Encrypt; `DOMAIN=localhost` gives a private-CA cert for smoke tests) and ports are published on IPv4 only (Docker's IPv6 proxy would hide client IPs — publish an A record, never AAAA) and the compose network is pinned to `172.28.0.0/24` so uvicorn's `FORWARDED_ALLOW_IPS` trusts only Caddy — that is what makes slowapi's `get_remote_address` see the real client (`tests/test_rate_limit_proxy.py`). Images are tagged `APP_TAG` = git commit (+ `-dirty-<diffhash>`), kept in `.deployed-tag`; always use `scripts/compose.sh` instead of bare `docker compose` or you get the `latest` tag. CSP is `script-src 'self'`, so no inline scripts in `frontend/index.html` (the theme pre-paint script is `public/theme-init.js`). The worker writes `/tmp/worker-heartbeat` (container healthcheck) and a `worker_heartbeats` row (admin page) every minute; `/api/health` does `SELECT 1`; logs are JSON when `LOG_FORMAT=json`, each request carrying `request_id` (Caddy sets `X-Request-ID`). Backups live in `/var/backups/apex-cycling` (root-owned) from `docker/backup.sh`; a new uploads directory the backend writes to must be created and chowned in `backend.prod.Dockerfile` (`/data/uploads` is) or the named volume comes up root-only. Platform-admin API: `GET /api/admin/overview` (`require_platform_admin`), page at `/admin` linked from the account menu.

Every router is mounted under `/api` (`API_PREFIX` in `app/core/config.py`, applied in `app/main.py`); route modules declare their prefixes without it. Tests' `AsyncClient` uses `base_url="http://test/api"` so test paths omit it too. In dev the Vite server proxies `/api` to the backend (`API_PROXY_TARGET`), in prod the edge Caddy does — the SPA always calls same-origin.

Domain modules under `backend/app/`: `auth`, `athletes`, `clubs`, `connections`, `ingestion`, `training`. Each (except `ingestion`) follows `models.py` / `schemas.py` / `router.py`, with a `service.py` where logic doesn't belong in the router.

**Model registration**: `app/db/models.py` re-exports every model class from every module purely so they register on `Base.metadata`. Any script or process that touches the ORM outside of going through `app.main` (seeding, one-off scripts, standalone test setups) must `import app.db.models` first, or SQLAlchemy relationship/FK resolution crashes at first use. `backend/tests/conftest.py` and `app/db/seed.py` both do this.

**Auth**: JWT access + refresh tokens in httponly cookies (`app/core/security.py`), not bearer headers. Access tokens are short-lived (15 min default); the frontend's `apiFetch` (`frontend/src/api/client.ts`) transparently retries once through `/auth/refresh` on a 401, coalescing concurrent refreshes into a single in-flight request. `app/auth/deps.py` provides `get_current_user`, plus `require_athlete_access` (athlete themself, their active coach, or their club's club_admin) and `require_club_admin` — route handlers needing athlete-scoped access must name the path parameter `athlete_id` for the dependency to bind correctly.

**Sessions & account** (`app/auth/`): a password change/reset sets `users.credentials_changed_at`, and any access/refresh token issued before it is rejected (`issued_before_credentials_change`) — that is how other devices get signed out. Reset links are single-use, hashed `PasswordResetToken` rows carried in the URL fragment; email goes out only when `SMTP_HOST`+`SMTP_FROM` are set (`app/core/mail.py`), otherwise a platform/club admin issues a link (`POST /auth/users/{id}/password-reset-link`) or the operator runs `python -m app.auth.cli reset-link <email>`. `app/auth/account.py` holds "export my data" and "delete account": **any new table with a `user_id`/`athlete_id` FK must be added to both** (`tests/test_account.py` fails if a row still points at a deleted user/athlete). The login/signup/reset/change/delete routes are rate-limited at 5–10/min per IP, which also bites repeated manual or Playwright runs — restart the backend to reset the in-memory counters.

**Activities** (`app/activities/`, Phase 7 — in progress, see `BACKLOG.md`): rides recorded outside sqorz (head unit/watch/power meter), owned by an athlete. `Activity` is the summary row (`source` upload / intervals_icu / strava, which also decides visibility — Strava data is owner-only per Strava's API terms, so coach/club-admin queries must exclude it); `ActivityStream` is one row of zlib-compressed little-endian float arrays per channel (`streams.py` `pack`/`unpack`, `None` ↔ NaN, time/distance float64, the rest float32); `ActivityPowerCurve` is mean-maximal power per standard duration. Originals live on the uploads volume (`UPLOADS_DIR`, default `/data/uploads`) as `activities/<athlete_id>/<sha256>.<ext>` via `storage.py`, the row keeping the relative path; uniqueness on `(athlete_id, file_sha256)` and `(athlete_id, source, external_id)` is what dedupes re-uploads and re-syncs. Account export/deletion cover these tables, and deleting removes the original files only after the deletion commits (`delete_originals_after_commit`). **Credentials**: `DataSourceConnection.credentials` is an `EncryptedJSON` column (`app/core/crypto.py`; Fernet, stored as `{"enc": token}` in a plain JSON column; plaintext legacy rows still read). `DATA_ENCRYPTION_KEY` may list several comma-separated keys for rotation; the dev default is public and `docker-compose.prod.yml` refuses to start without a real one, for both backend and worker. The prod worker will also need the uploads volume once it downloads files (T7.5).

**Activity import** (T7.2; `parsers/`, `summary.py`, `service.py`, `router.py`, `/api/athletes/{id}/activities`): `parse_activity_file(bytes)` sniffs the format from the content (FIT magic / TCX or GPX root element, never the file name) and returns a `ParsedActivity` — `time_s` strictly increasing plus a `channels` dict that holds only the channels the file carries, `None` for dropouts. `build_activity` is the shared normalizer: sorts, drops repeated timestamps, blanks implausible readings (power > 3000 W, HR 0…), derives distance from GPX positions and speed from distance, and caps samples (`MAX_SAMPLES`). FIT uses `fitdecode` with CRC and errors set to RAISE; TCX/GPX are read with `defusedxml` (entity expansion refused) and hand-written local-name walkers instead of gpxpy, which is why `gpxpy` isn't a dependency. `summary.py` gives the headline numbers: samples are weighted by the time until the next one (gaps over 10 s are pauses and count 1 s), average cadence skips zeros, elevation gain ignores changes under 2 m, moving time is the device timer else time above 0.5 m/s. `import_activity_file` dedupes twice — by `(athlete, sha256)` and by "same ride" (start within 5 s, duration within 10 s, which also catches the same recording as FIT and TCX or an upload followed by a sync) — and does the insert inside a savepoint so a lost race on the unique index degrades to `duplicate`; callers commit. Upload answers per file (`created` / `duplicate` / `failed` + reason), up to 20 files of `MAX_ACTIVITY_FILE_BYTES` (15 MB). Only the athlete (or club admins of a managed athlete: `speaks_for_athlete`) may upload or delete; coaches read. Every read goes through `visible_activities(athlete, viewer)`, which drops Strava rows for anyone but the owner — use it for any new activity query a coach or admin can reach. Tests build FIT files with `tests/fit_builder.py` (a minimal writer; no real device file is committed).

**Power metrics & training load** (T7.3; `app/analysis/metrics.py` pure, `app/activities/metrics_service.py` persistence): power is analysed as a 1 Hz series (`resample_1hz`: latest reading held until the next, dropout = 0 W; a recorder pause of more than 10 s is zeros for the power curve so an effort can't straddle a stop, but *skipped* for normalized power so a stop doesn't dilute it). `ActivityPowerCurve` holds the best mean power at `STANDARD_DURATIONS_S` (not forced monotone — a 3 s window can beat the best 2 s one); NP = 30 s rolling mean ^4; IF = NP/FTP; TSS = moving hours × IF² × 100. They're computed on import (`apply_power_metrics`), TSS uses the FTP in force on the activity's *local day* (club timezone, UTC without a club) — or the athlete's earliest FTP when the ride predates every entry and is re-derived from the stored NP whenever the athlete's metrics are saved or deleted (`refresh_tss`, called from `athletes/router.py`) — so no stream decoding on an FTP change. `python -m app.activities.cli recompute-metrics [--athlete ID]` rebuilds everything from the stored streams. **Training load** (`GET /athletes/{id}/training-load`): per day, an activity counts its TSS, else `srpe_training_stress(rpe, duration)` (IF = 0.30 + 0.08×RPE, a heuristic), else nothing (counted in `unrated_activities`); rated sqorz sessions (`TrainingEvent.rpe`, duration = start→end timestamps, ≤ 6 h) add sRPE load. CTL/ATL are exponential (τ 42/7 days, `1-exp(-1/τ)`) from the first day with load; TSB is the *previous* day's CTL−ATL (form going into the day). `GET /athletes/{id}/power-curve?start&end` is the best per duration with the activity that set it. Activities carry the athlete's own `rpe`/`notes` and a `name` (`PATCH …/activities/{id}`, data owner only). Both endpoints and the load use `visible_conditions`, so Strava activities never reach a coach. A rated sqorz session is skipped when a visible activity linked to it already carries load.

**Activity ↔ sqorz session fusion** (T7.4; `analysis/fusion.py` pure, `activities/fusion_service.py`): `Activity.training_event_id` links a recording to the `TrainingEvent` it contains (several recordings may share one session). `clock_offset_s` is *added to device timestamps to get sqorz time* (device clock behind ⇒ positive); `session_link_manual` marks a link or unlink the athlete chose, which auto-linking never touches (unlinking is sticky). Auto-linking runs on import (`auto_link_activity`) and after every sqorz sync (`sync_session_links`, via `SqlAlchemyRecordsAdapter.recompute` — the ports' "derived data" hook): it matches the ride, widened by 5 min of clock slack, against each session's lap span (first lap − 30 s … last lap + 90 s) and needs ≥ 50 % of that span covered; it also re-estimates the offset of unlocked links from the last 3 days as more laps arrive. The offset is estimated by `estimate_clock_offset`: Pearson correlation between the head unit's speed averaged over each sqorz lap window and sqorz's lap speed (1/lap time, so the track length isn't needed), searched ±300 s (2 s steps, then 0.25 s), after dropping laps outside 0.5–2.5× the median lap time (sqorz has 6 s "laps" from missed crossings). It is applied automatically only when `confident` (r ≥ 0.9 and 0.1 above the best rival > 30 s away); otherwise 0, and steady-pace sessions are deliberately reported unconfident — the athlete sets it with `PUT …/activities/{id}/session {external_event_id, clock_offset_s?}` (`DELETE` unlinks, `GET …/session/suggestion` previews). Checked on the LS-03407 fixture's real lap sequences with synthetic speed traces: within ~1 s for 7 of 8 sessions. Session detail and efforts then carry `avg_power_w / avg_heart_rate / avg_cadence` per lap and per effort (`window_mean` over the lap window shifted by the offset, from the first linked recording that covers it) and a `activities` list; both go through `visible_conditions`, so a coach never gets Strava-derived numbers. `delete_athlete` removes activities before sessions because of the FK.

**Intervals.icu sync** (T7.5; `app/ingestion/intervals/` — the sqorz ports/repository/DI shape: `ports.py`, `dtos.py`, `client.py`, `repositories.py`, `service.py`, `factory.py` composition root; routes in `app/connections/intervals_router.py`, `/api/athletes/{id}/intervals` GET status / PUT connect / POST sync / DELETE disconnect, data owner only): the athlete pastes their Intervals.icu API key; it is checked against `GET /athlete/0` (Basic auth, user `API_KEY`), stored encrypted in `DataSourceConnection.credentials` (`provider=intervals_icu`, `external_id` = their Intervals athlete id, so one Intervals account maps to one athlete) and never returned. `IntervalsSyncService.sync` lists activities (`oldest` = last sync − 2 days, or `INTERVALS_BACKFILL_DAYS`=365 on the first), keeps rides and gym sessions (`RemoteActivity.is_wanted`: any "ride" type, cycling, `WeightTraining`) that aren't Strava-sourced and have no `_note` (Intervals.icu can't serve Strava data), skips ids already imported for the connection, downloads the original file (`/activity/{id}/file`, gunzipped with a size cap) and feeds it to the same `import_activity_file` as an upload (so it is deduped, scored and linked). A gym session with no file (typed in by hand), or whose file has no usable samples, is kept from the numbers the activity list gives (`import_summary_activity`: UTC `start_date`, elapsed/moving time, average/max HR, `icu_rpe` → `rpe`, description → `notes`): no `ActivityStream` row (so `/streams` is 404 and the frontend shows just the stat tiles), no original, no power metrics or session linking; its training load comes from the RPE. Rides without a file are still skipped. It downloads at most `INTERVALS_MAX_DOWNLOADS_PER_RUN`=100 newest-first and only advances `last_synced_at` when it saw everything, so a long history arrives over several runs; each activity is committed on its own. A ride already uploaded by hand is recorded (external id on the existing row) instead of duplicated or refetched. A refused key (401/403) marks the connection inactive until the athlete reconnects; 429 or an outage fails the run but keeps polling. Each run is an `IngestionRun` (new `imported_count`) = the sync history. Connecting kicks off the first sync as a FastAPI background task; the worker (`runner.py`, `jobs.poll_intervals_connections`) repeats it every `INTERVALS_POLL_INTERVAL_MINUTES`=30, which is why the worker has the uploads volume and `DATA_ENCRYPTION_KEY`. Tests inject a fake client via the `get_intervals_client` / `get_session_factory` dependencies. Unverified against the live service: only the documented behaviour (basic auth, `athlete/0`, `oldest`/`newest`, gzip original) is relied on.

**Strava sync** (T7.6; `app/ingestion/strava/` same shape — client, dtos, `mapping.py` pure, ports, repositories, service, factory; routes in `app/connections/strava_router.py`): off unless `STRAVA_CLIENT_ID` + `STRAVA_CLIENT_SECRET` are set (register the app at strava.com/settings/api with the deployment's domain; a new app may connect only one athlete until Strava approves it). OAuth: `GET /athletes/{id}/strava/authorize-url` → Strava consent (`activity:read_all`) → `GET /api/strava/callback` (public; identified by a signed 15-min `state` JWT, not the login cookie, which may have expired) → exchanges the code, stores `{access_token, refresh_token, expires_at, athlete_name, scope}` encrypted, starts a background sync and 303-redirects to `/import?strava=connected|denied|error`. The sync lists rides (`after` = last sync − 2 days or 90-day backfill, ≤ 3 pages), skips manual/non-ride/known ones **and any ride the athlete already has from another source (`find_same_ride`, checked *before* fetching streams — Strava's limits are 100 req/15 min and 1000/day for the whole app, hence `STRAVA_POLL_INTERVAL_MINUTES`=180, ≤ 15 stream fetches per run, and the worker's round stops at the first 429)**, then fetches streams (no files exist) and stores them via `import_parsed_activity` with `source=strava`, no original file. Power is kept only if Strava says `device_watts` (otherwise it is Strava's estimate). Access tokens refresh before expiry and the rotated refresh token is committed immediately. **Strava terms**: Strava activities are owner-only everywhere (`visible_conditions`), carry `external_url` for the required link back to Strava, and are deleted when access ends — `disconnect` (also deauthorizes at Strava), a refused refresh (`revoke`), or a verified deauthorization webhook; an upload/Intervals file of the same ride replaces the Strava copy (keeping the athlete's rpe/notes/name) since the athlete's own file is the better, shareable copy. Optional webhook (`/api/strava/webhook`, `python -m app.ingestion.strava.cli subscribe`): events are only hints — `create` runs a sync, `delete` and deauthorize are acted on only after Strava confirms with the athlete's own tokens, since the endpoint is public (`STRAVA_WEBHOOK_SUBSCRIPTION_ID` filters foreign subscriptions). Settings treat empty env vars as unset (`env_ignore_empty`), because compose passes unset optional vars through as "". Don't feed Strava data to anything beyond showing it to its owner (Strava's terms also forbid using it for model training or sharing it, so it must stay out of club leaderboards, T9.4).

**Activities frontend** (T7.7; `features/activities/`, routes `ImportPage` `/import`, `LogPage` `/log`, `ActivityPage` `/activities/:id`, `PowerCurvePage` `/power`; i18n namespace `activities`): the Import hub is the upload dropzone (`uploadQueue.ts` screens extension/size, then **one request per file** so each file has its own status, waiting and retrying on 429), the Intervals.icu card (paste API key), the Strava card (redirect to `authorize-url`, back at `/import?strava=connected|denied|error`; shows "not set up" when the server has no Strava app, the owner-only notice and the sync history) and the sqorz card. `apiFetch` skips its JSON Content-Type for `FormData` bodies. The Log merges sessions and activities (`logItems.ts::mergeLog`: a recording linked to a listed session folds into its session row) as a list or Monday-first month calendar (`?view=calendar&month=YYYY-MM`; ticks on phones). A recording linked to a sqorz session has no page of its own: `/activities/:id` redirects to the session's **Ride tab** (`/sessions/:id?tab=ride&recording=`, a picker when several recordings share it), and link/unlink write the returned activity into the `["activity", …]` cache so neither page redirects on a stale copy. Both pages render the same `RecordingView` (+ `RecordingActions` in the header), except that the session shows the streams chart (`RecordingStreams`) on its Overview tab rather than the Ride tab — the chosen `?recording=` follows across tabs; there `StreamChart` gets a `SessionOverlay` (`sessionOverlay.ts`: efforts shaded, sqorz lap speed on the speed chart, a dashed "cadence from gear" = recorded speed ÷ `development_m` of the gear in force (an effort's own gear over its span, else the session's; `sessionGearing`) on the cadence chart, the axis on sqorz's clock via `clock_offset_s`, opening zoomed on the session). `RecordingView`: stat tiles, `StreamChart` (one small chart per channel sharing the x axis, time or distance, a Brush strip zooms all of them and the channel averages follow the zoom; data from `/streams` thinned server-side), `ZoneBars` (zones need FTP / max HR in Settings), the ride's own `CurveChart`, the sqorz link panel (suggestion, manual link/unlink, clock offset) and notes/RPE editing — read-only for a coach (`canEdit = !viewing || viewing.user_id === null`). `FitnessCard` (CTL/ATL/TSB, Home hides it until there is load, Progress always shows it) and `/power` (period vs the period before or all time, W or W/kg) read `/training-load` and `/power-curve`. Lap table, CSV and effort cards gain power/HR/cadence columns when a recording is linked. Strava rides: show `external_url` ("View on Strava") and the owner-only badge. Nothing here has been checked against a real Strava or Intervals.icu account.

**Aero lab** (Phase 8; `app/analysis/aero.py` pure, `app/aero/`): CdA from a sqorz session plus its linked recording. Per lap, `η·P/v − ½·m_eff·(v_exit² − v_entry²)/L = ½ρ·CdA·v² + Crr·m·g` with v = track length / sqorz lap time (not the wheel sensor) and P the recording's mean power over the lap window (`fusion_service.Recording.stats`, ≥ 90 % coverage, so the clock offset and `visible_conditions` apply — a coach never gets a Strava-derived CdA); entry/exit speeds are the means with the neighbouring laps of the same effort. The automatic pick drops excluded laps, laps without power, the first lap of each effort, laps under 8 m/s, laps more than 3 % off a neighbour's speed and laps whose power spread is > 25 % of its mean; a hand-picked `lap_ids` replaces it (excluded/power-less laps still never count). Crr is fitted (OLS on v²) only with ≥ 6 laps spanning ≥ 10 % of speed and a plausible result (0.001–0.01), otherwise held at the given `crr` or `DEFAULT_CRR`; `r_squared` is null when every lap is one speed. `POST /athletes/{id}/sessions/{event}/aero` only computes: inputs default to the track's `default_temp_c` (else 20 °C) / `elevation_m`, 50 % humidity, the profile weight on the session day (else the first one entered after it) + 8 kg bike, and the answer carries `problem` (`no_track_length` / `no_weight` / `no_power` / `too_few_laps`) when there's no fit. **Aero tests** (`aero/models.py::AeroTest`, `/athletes/{id}/aero-tests` CRUD, `require_athlete_access` so coaches can set them up too) store only inputs — session, track, `lap_ids` (null = automatic pick), setup text, `AeroInputs` overrides (null = default) — and recompute the estimate on every read (`list_tests` loads each session once), so there are no derived rows to keep in sync and the Strava rule holds per viewer. `delete_athlete` removes them before sessions (FK).

**Equipment & estimated cadence** (T9.1; `app/equipment/`, `/api/athletes/{id}/bikes|gears`, page `/equipment`, `features/equipment/`, i18n namespace `equipment`): `Bike` (name, bike-only `weight_kg`, notes, tire + its `crr`; the bike dialog's tire dropdown comes from the hand-maintained `frontend/src/features/equipment/tires.json` — `{brand, name, type, size (integer mm), crr}` entries, stored on the bike as the joined label, checked by `gear.test.ts` — and fills both fields, which stay free to type for an unlisted tire) owns `GearSetup`s (chainring, cog, `rollout_mm` = wheel travel per turn as ridden). A gear is assigned to a session (`TrainingEvent.gear_setup_id`) or to one effort (`TrainingLap.effort_gear_setup_id` on the effort's *first lap*, like `effort_label`; it overrides the session's) through dedicated `PUT …/gear` endpoints, which refuse another athlete's gear (`UnknownGear`) — not through `SessionUpdate`. Neither column is ever written by the sqorz upsert. `add_gear_to_session` / `add_gear_to_efforts` (called from `training/router.py`, the same enrich-after-fetch shape as the activity metrics) fill `est_cadence_rpm` per lap (track `length_m` ÷ lap time → `physics.cadence_from_speed_rpm`) and per effort (distance ÷ total time); no track length or no gear means null. It assumes the rider never coasts, which holds on a fixed gear. The aero lab uses the session gear's bike weight as the default `bike_kg` (an explicit input still wins). Saved bikes are offered wherever a bike weight or gear is typed (`equipment/BikeSelect.tsx`; `gear.ts::bikeOfWeight`/`gearOf` show which saved bike/gear the typed values are): the tools prefill `bikeKg` from the first weighed bike and the gearing fields from the first gear and have pickers that write those values into the URL (share links stay self-contained); picking a bike also writes its Crr (Tools rider card, aero lab; the aero lab's blank choice goes back to the automatic Crr), and a new gear's rollout starts at the standard one for the bike's tire width (`gear.ts::bikeRolloutMm`: listed tire's size or a typed "23 mm" → the 700×23c preset); the aero lab's picker types the bike weight in and its name pre-fills the saved test's bike; a goal has an optional `bike_id` (migration 0012, nulled when the bike is deleted). Deleting a gear or bike detaches it from sessions/efforts instead of refusing; `delete_athlete` and `build_export` cover both tables.

**Goals** (T9.2; `app/goals/`, `/api/athletes/{id}/goals`, `features/goals/` `GoalsCard` on Home, i18n namespace `goals`): a `Goal` stores only the target (`event_key` + `start_type` from `STANDARD_EVENTS`, optional `track_id` = count only results there, `target_time_ms`, `target_date`) and `baseline_ms`, the best at creation (the start of the progress bar); the event and start are fixed after creation. Best, gap, `achieved`, progress and days left (club timezone) are derived on every read from `get_records_board`. The prediction (`goals/prediction.py` pure): power = best mean power over the standard duration nearest the target time (ratio, `power_curve` of the last `POWER_WINDOW` = 120 days, through `visible_conditions` so a coach never gets Strava-derived power), scaled until the simulated *average* (which includes the standing-start surge) matches it, ridden through `physics.simulate` with the CdA of the newest aero test that has a fit and the latest weight + the goal's bike weight (else the bike weight that aero test used); a flying lap needs a track with `length_m`. When an input is missing `prediction_problem` says which. Coaches and club admins can set goals through `require_athlete_access`.

**Planned sessions** (T9.3; `app/planning/`, `/api/athletes/{id}/planned-sessions`, `features/plan/`, i18n namespace `plan`): a `PlannedSession` is a date + title + description + `targets` (JSON list of `PlannedEffort`: label, reps, optional standard `event_key`/`start_type`/`target_time_ms`, a time only with an event, optional `gear_setup_id` = one of the athlete's gears, checked on write and read back with a `gear_label`; a deleted gear just reads as none, nothing is rewritten) put on an athlete's calendar by anyone passing `require_athlete_access`, with `status` planned/done/skipped and `training_event_id` (the sqorz session actually ridden). Two permission levels, both computed per viewer into `can_edit` / `can_mark`: the author and the athlete's side (`speaks_for_athlete`) edit or delete; **only the athlete's side** changes `status` or links a session, so a coach can plan but never answer for the athlete. Linking (`PUT …/session {external_event_id}`) makes it done; setting any status but done, or `DELETE …/session`, unlinks. `created_by_user_id` is nulled when the author deletes their account (`delete_account`); `delete_athlete` removes plans before sessions (FK). Frontend: one `PlanDetailDialog` (what is asked + the viewer's actions; suggests sessions within ±2 days to link) opened from the Home `PlannedSessionsCard` (unanswered plans from 14 days back) and from dashed chips on the Log calendar; `PlanDialog` creates/edits. A coach plans while "viewing as" the athlete.

**Club leaderboard** (T9.4; `app/clubs/leaderboard.py`, `GET /api/clubs/{id}/leaderboard`, `features/clubs/LeaderboardPanel.tsx`, Settings → Privacy): opt-in is per roster entry, `AthleteClub.leaderboard_opt_in` (an athlete on two rosters agrees to each board separately; `AthleteRead.leaderboard_club_ids`), so leaving a club deletes the entry and the consent with it and rejoining never revives it. Only `speaks_for_athlete` (the athlete, or a club admin for a managed athlete) may set it, through `PUT /athletes/{id}/clubs/{club_id}/leaderboard {opt_in}` (422 when the athlete isn't on that roster); a coach or club admin who can otherwise edit the profile gets 403. The board lists, for one track of the club's linked facilities, one event and start, each opted-in roster athlete's best of `personal_records` and manual results that name the track (equal times share a rank), filterable by sex and UCI category (computed as of today); it exposes display name, time, date, sex, category and source, never an id. Strava activities feed neither source, which keeps them out, as the Strava terms require.

**Session insights** (B1; `app/training/insights.py` pure, `insights_service.py`, `GET /athletes/{id}/insights?days&limit` and `…/sessions/{event}/insights`, `features/insights/`, i18n namespace `insights`): headlines derived on every read from the same inputs as the records (`records_service.load_session_inputs` → `results_of` and the detected efforts), nothing stored, so they follow lap edits and exclusions. Kinds: `personal_record` (beats every earlier session's result for its track/event/start; carries `milestone_ms` when it crossed a round time — step 1 s under a minute, 5 s under five, else 10 s), `season_best` (calendar year; needs an earlier result *that season*), `best_nth_lap` (efforts ≥ 4 laps, same start type and season; one per session and track, the biggest improvement; skipped when that lap already is a `lap` record), `most_consistent` (lap-time CV, a standing start's first lap left out, only against efforts of a similar lap count). A first-ever result is never a headline. `Insight.key` is the stable identity the notifications dedupe on. Sqorz data only (manual results don't count), so Strava never enters. Frontend: `SessionInsights` banner, Home `WhatsNewCard` (30 days), and "Sync now" toasts the headlines that weren't there before (`useNewInsightsAfter`).

**Share card** (B2; `features/share/`): `shareCard.ts` draws a fixed dark 1080×1350 card on a canvas (the velodrome from `velodromeGeometry`, time, delta vs the previous best, lap bars; fixed palette on purpose — an image people post can't follow the theme), `cardModels.ts` builds the model from a record or an effort (pure, formatted by the caller), `renderShareCard.ts` waits for the web fonts and either calls `navigator.share({files})` or saves the PNG. The `ShareButton` sits on record badges and effort cards.

**Notifications** (B3; `app/notifications/`, `/api/notifications`, `features/notifications/`, i18n namespace `notifications`): a `Notification` row is the bell entry *and* the outbox. `service.notify(db, user_id, kind, payload, dedupe_key=)` (flushes, never commits — producers call it inside their own transaction) reads the user's preferences (`NotificationPreference.prefs`, overrides of `kinds.DEFAULT_PREFERENCES`: in_app/push/email per kind; all on except email for records) and stores `in_app`/`want_push`/`want_email`; with every channel off nothing is stored. `payload` holds names and ids, never text: the bell translates it client-side (`NotificationItem`), push/email text comes from `messages.py` in the user's saved locale (French when none). The worker (`runner.send_notifications`, every minute) calls `deliver_pending`: Web Push via `pywebpush` (`push.py`, off unless `VAPID_PUBLIC_KEY`+`VAPID_PRIVATE_KEY`; dead 404/410 subscriptions are deleted) and email via `core/mail`, then sets `delivered_at` whatever happened — so the worker also needs `SMTP_*`, `VAPID_*` and `APP_BASE_URL` (both compose files pass them). Producers (`producers.py`): `notify_new_records` (called from `SqlAlchemyRecordsAdapter.recompute`, i.e. after every sqorz sync; one notification per session, ≤ 5 listed, only sessions in the last 7 days, each record once — told keys live in `payload.insight_keys`), `notify_sync_failed` (through the optional `SyncFailureNotifierPort`; once per failure streak; not for a forced "Sync now"), `notify_comment` (athlete + active coaches + people already in the thread − author), `notify_coach_request` (from `coaching._open_link` only when the link's state changed), `notify_plan_added` (someone other than the athlete). A new notification kind: add it to `NotificationKind`, `DEFAULT_PREFERENCES` follows, add its text to `messages.py` and the `notifications` namespace, and a producer. `push-sw.js` (public/, pulled into the generated service worker with `workbox.importScripts`) shows pushes and opens only same-app paths. New tables with a `user_id` are covered by account export/deletion (`notifications`, `notification_preferences`, `push_subscriptions`). Operator: `python -m app.notifications.cli generate-vapid`.

**Sprint metrics & pacing** (C2/C4; `app/training/sprint.py`, `pacing.py` pure, attached to `EffortDetail` by `service._effort_detail`): `CheckpointCrossing.distance_m` carries the loop's recorded distance. A gate is *placed* by that distance, else by name (`NNNm` = distance left to the finish, `Finish` = the line; real sqorz exports send null distances), so a top speed needs no track length but the launch (standing start's first placed gate → average acceleration 2·d/t²) does. Pacing is over the finished, non-excluded laps minus a standing start's first lap: CV, fade (last third vs first) and each lap's % deviation from the mean. Both are derived on every read.

**Compare & planned vs actual** (C1/C3): `/compare?a=&ae=&b=&be=` (`features/compare/`, i18n `compare`) overlays two efforts — `a`/`b` are session ids, `ae`/`be` an effort's first lap id (the longest effort when absent); `compare.ts` is pure and tested. `planning/matching.py` (pure) expands a plan's targets into reps and gives each the first later effort with a result for its event and start; `planning/comparison.py` scores each effort of the linked session with `records.session_results` (views via `records_service.view_times_of`) and `GET …/planned-sessions/{id}/comparison` serves it (409 until a session is linked). `training/service.detect_session_efforts` is the one place efforts are detected and numbered.

**Coach v2, seasons & CP** (Sprint D): `athletes/dashboard.py` cards now carry `form` (CTL/ATL/TSB via `metrics_service.training_load` *as the coach*, so Strava stays out), `plan` (`PlanCompliance`: the last 28 days' plans, `missed` = still `planned` after their day, plus plans coming up in 7 days), `goal` (the nearest open goal, else the latest reached one; built from `goals.service._best/_progress` on the records board, *not* the full goal read with its aero-fitting prediction) and `next_race`. `GET /coach-links/squad?event_key&start_type[&track_id]` (`athletes/squad.py`) ranks the actively coached athletes on `get_records_board` (sqorz + manual only). **Seasons & races** (`app/seasons/`, `/api/athletes/{id}/seasons|competitions|calendar-feed`, public `/api/calendar/{token}.ics`, `features/season/`, i18n `season`, page `/season`, Home `NextRaceCard`): a `Season` is only a start date (it ends the day before the next one; `season_bests` is pure over `_Entry` rows — computed results from `load_session_inputs` + manual results — and compares with the best *before* the start); a `Competition` has A/B/C priority → taper days in `seasons/planning.py` (pure; 10/5/0) and an optional goal; `TrainingEvent.is_race` is set from the session Notes tab through `SessionUpdate` and never by sync. The calendar feed is `CalendarFeed.token_hash` (sha256, one per athlete, shown once when made, replacing it kills the old link; managed only by `speaks_for_athlete`) → `seasons/ics.py` (pure RFC 5545 writer: CRLF, 75-octet folding that never splits a character, all-day events) filled in `service.calendar_for_token` with non-skipped plans, races and the taper start, in the athlete's saved locale (French when none); the route is rate-limited and public, the secret is the credential. New athlete tables `seasons`/`competitions`/`calendar_feeds` are in account export (`seasons.csv`, `competitions.csv`) and `delete_athlete` (competitions before goals). **Shared helpers**: `records_service.best_entry` is the one "fastest entry at an event/start/track" rule (goals, squad and dashboard use it; `goals.service.progress_towards` is the goal progress); deleting a goal nulls `Competition.goal_id` first. `training_load` ignores load older than 252 days before its window. The race countdown (`days_until`, `days_to_taper`, `phase`) is computed server-side in the club time zone — the client never recomputes it. **CP/W′** (`analysis/critical_power.py` pure, `GET /athletes/{id}/power-profile?days=14…365`, `metrics_service.power_profile`, `PowerProfileCard` on `/power`): least squares of work on time over the standard durations 3–20 min of the best power curve in the window (`visible_conditions`), needs a point ≤ 6 min and one ≥ 12 min and a physical line (rising work, non-negative W′ intercept; a loose fit is returned with its R² and the client flags it); FTP suggestion = 95 % of the best 20 min, returned only when it differs from the FTP in force by > 2 %.

**First-run checklist** (B4; `features/onboarding/`): `buildChecklist` (transponder, weight, club, coach — the last two optional) from the athlete's own assignments, current weight, `club_ids` and active coach links; Home shows it only for the signed-in user's own athlete, until it's complete or hidden (`localStorage`, per athlete). `/import#sqorz` scrolls to the sqorz card (`#sqorz` wrapper, scrolled again after 700 ms because the cards above load async) and the card reports "Found N laps in M sessions" after adding a transponder or a manual sync. A manual sync invalidates sessions, records, tracks and insights (`useConnections.invalidateTrainingData`), since queries stay fresh for 60 s.

**Sqorz ingestion** (`app/ingestion/sqorz/`): being incrementally refactored to a ports/repository/DI pattern to decouple business logic from SQLAlchemy (see `BACKLOG.md` "Refactoring of backend"). Current shape for the client+service layer (step 1, done):
- `ports.py` — `Protocol` interfaces (`SqorzClientPort`, `*RepositoryPort`s, `SnapshotNormalizerPort`, `UnitOfWorkPort`). `service.py` must only depend on these, never on SQLAlchemy directly.
- `dtos.py` — plain dataclasses/records passed across the port boundary (e.g. `DataSourceConnectionRecord`, `IngestionRunRecord`).
- `repositories.py` — concrete SQLAlchemy-backed implementations of the repo ports.
- `normalizer_adapter.py` — adapts the concrete `normalizer.py` (still un-refactored, see below) to `SnapshotNormalizerPort`.
- `factory.py` — the one composition root (`build_sqorz_ingestion_service`) wiring concrete adapters into `SqorzIngestionService`; nothing else should construct that service directly.
- `ports.py` also has `SyncFailureNotifierPort` (optional constructor argument; the factory wires `SqlAlchemyFailureNotifier`) so the service can announce a failed poll without importing notifications.
- `service.py` — `SqorzIngestionService.ingest`: fetch → dedupe by content hash against the latest stored `RawSnapshot` → normalize + recompute records, but an *unchanged* payload is skipped unless an assignment was added/edited since `DataSourceConnection.normalized_at` (`TransponderAssignment.updated_at`, so a new assignment still retroactively attributes previously-unowned laps), `normalizer_version` differs from `NORMALIZER_VERSION` in `service.py` (**bump it whenever the normalizer or the records derived from its rows change**, or existing payloads are never re-read), or the caller passes `force` (the manual "Sync now" does) → mark the `IngestionRun` success/failed → commit.
- `normalizer.py` — the actual sqorz-payload → training-tables normalization logic; **not yet refactored** to the ports pattern (deferred, same pattern to reuse when picked up).

Tests for the refactored layer (`backend/tests/test_sqorz_ingestion_service.py`) fake every port directly — no DB, no HTTP — as the reference pattern for testing this style of service.

`app/ingestion/jobs.py::poll_active_connections` (invoked by `app/ingestion/runner.py`'s APScheduler loop) only polls sqorz connections with a currently-active `TransponderAssignment` (assignment window covers today).

**Clubs** (`app/clubs/`): any user can create a club and becomes its `club_admin` (`ClubRole`: athlete / coach / club_admin). Joining as an athlete puts the user's self-athlete on the roster (an `athlete_clubs` row, `Athlete.join_club`/`leave_club`; a self-athlete can be on several rosters, a managed one is on the single roster of the club that created it; leaving or a role change off `athlete` drops that club's row only). `AthleteRead` carries `club_ids`; `Athlete.club_links` is always loaded (selectin) and every check reads it, so change it through `join_club`/`leave_club` and use `on_roster_of(club_ids)` in queries. `GET /clubs/{id}/athletes` rows carry `category` (UCI code as of today) for the roster's column and filter. A club admin of *any* of an athlete's clubs gets `require_athlete_access`, and the TSS day boundary uses the timezone of the club joined first; managed athletes are `Athlete` rows with `user_id` null that club admins create (`POST /clubs/{id}/athletes`) and then run through the normal `/athletes/{id}/…` endpoints (profile, metrics, transponders) via `require_athlete_access`. Invites (`club_invites`) are hashed tokens carried in the URL fragment (`/join#token=…`), role athlete or coach only (admins are promoted in the member list), with expiry and `max_uses`; preview/accept take the token in the request body (`/api/invites/preview|accept`) so it stays out of access logs; email goes out when SMTP is set, otherwise the admin copies the link. A club always keeps ≥1 admin (demote/remove/delete-account are refused for the last one while the club has other people or managed athletes; a one-person club is deleted with its account — `clubs/service.py`). `club_sqorz_accounts` links a club to a sqorz facility so its admins can edit that facility's tracks; only platform admins create links (API or `python -m app.clubs.cli link-sqorz <slug> <account-id>`). `auth/account.py::delete_athlete` is the shared "remove an athlete and all their data" used by account deletion and managed-athlete deletion — new athlete-owned tables go there and in `build_export`.

**Coach–athlete links** (`app/athletes/coaching.py`, `coach_router.py`, `/api/coach-links`): a link needs both sides — whoever asks creates it pending on the other side (`pending_athlete_acceptance` when a coach asks, `pending_coach_acceptance` when the athlete does); the other side accepts, or declines/cancels/revokes via `/revoke` (all end `REVOKED`; asking again reopens the same row); both sides having asked activates it. Only `ACTIVE` links grant access (`require_athlete_access`). A managed athlete has no login, so their club's admins speak for them: an admin assigns a coach of the club and the link is active at once (`speaks_for_athlete`). `POST /coach-links` takes `acting_as` coach|athlete and names the other person by id (limited to people you share a club with — roster for coaches, coach/admin members for athletes) or by email; the email form always answers the same 202 so it can't reveal which addresses have accounts. `GET /coach-links/{athletes,coaches,inbox}` list my athletes, my coaches (optionally of a managed athlete) and requests waiting for my answer; `GET /coach-links/dashboard` (`athletes/dashboard.py`) is the coach's summary card per actively-coached athlete (last session, this vs previous 7 days' sessions/laps/avg RPE — "form" is recent load, not a fitness model — records in the last 14 days, transponders whose latest sync failed, unread comments).

**Session comments** (`app/training/comments_*.py`, `/api/athletes/{id}/sessions/{event}/comments`, `/api/comments/inbox`): a thread per athlete session (`SessionComment` hangs off the private `TrainingEvent`) between the athlete and anyone passing `require_athlete_access` (active coach, club admin). Authors edit/delete their own; the athlete's side (`speaks_for_athlete` — the athlete, or a club admin for a managed athlete) can delete any. "New" is tracked per (user, session) by `SessionCommentRead.last_read_at` (`POST …/comments/read` when the thread is shown; posting also marks it read); the inbox lists sessions with unread comments by others across the user's own athlete, athletes they actively coach and clubs they administer. Deleting an account deletes the comments it wrote; deleting an athlete deletes the threads on their sessions.

**Training data model** (`app/training/models.py`): `Track`/`TrackLoop`/`TrackView`/`TrackViewLoop` are a shared facility dimension scoped by sqorz's `account_id` (not by apex-cycling `club_id` — a session can span athletes from many or no clubs). `TrainingEvent` and everything under it (`EventClass`, `EventTrack`, `TrainingLap`, `LapSegmentTime`) is instead a private per-athlete copy — two athletes at the same physical sqorz event each get independent rows, since this data is meant to be manually editable per-athlete without side effects. `LapSegmentTime.time_ms` is cumulative elapsed time since lap start (matches sqorz's `lapTimes` 1:1) — never sum it directly; whole-lap/view/segment durations are derived by boundary subtraction in `app/training/service.py` (`_whole_lap_time_ms`, `_view_time_ms`, `_segment_deltas`).

**Frontend records & session page**: `features/records/` (board grouped by place, record-history step chart, manual-result dialog; `timeInput.ts` parses typed times like `1:12,345`) and `features/training/session/` (Overview / Laps / Efforts / Notes / Comments tabs, `?tab=` in the URL; `lapTable.ts` builds the split columns and the CSV). The Progress page maps standard events to `custom_distance` + `start_type` in `features/training/progression.ts` and only offers them for tracks with a length set. Pure helpers live in plain `.ts` files next to the components (lint's only-export-components rule).

**Efforts, distances & records** (`app/training/`): pure, directly-tested modules with the DB-facing parts split off — `efforts.py` (group laps into continuous efforts: next lap starts where the previous ended, an unfinished lap always ends its effort; standing vs flying from the first-lap time profile because sqorz's `from_start` is True on every lap; P1/P2 half-lap splits across the whole effort), `distances.py` (`STANDARD_EVENTS`; N-lap windows inside an effort, N = distance / `Track.length_m`, so tracks without a length only get single-lap/F200 records), `records.py` (per-session results → all-time best → improvement chain). `records_service.py` persists `personal_records` (derived, rebuilt by `recompute_personal_records`, never edited) and CRUD for `manual_results`; the board merges both, best time per place/event/start type. `SqorzIngestionService` recomputes records for the athletes `normalize` reports via `AthleteRecordsPort`; after any change to laps or `length_m` run `python -m app.training.cli recompute-records [--athlete ID]`. Athlete edits (`edit_service.py`; columns on `TrainingEvent`/`TrainingLap` that the sqorz upsert never writes, so they survive re-syncs): session `title_override`/notes/RPE/tags, lap `excluded`/`label`, and `effort_label` on the *first lap of an effort* (efforts are computed, so there's no row to hang it on). An excluded lap stays in its effort so neighbours stay chained, but never counts as a best lap, in a record window, the F200 or progression; toggling it recomputes records. Track settings (`tracks_service.py`, `PATCH /api/tracks/{id}`): `Track.length_m`/`indoor`/`elevation_m`/`default_temp_c` plus a `hidden` flag on loops (not drawn on the diagram) and views (not offered in pickers) — display-only, never written by sync; new loops named "Courbe…" start hidden (`DEFAULT_HIDDEN_LOOP_PREFIXES` in the normalizer). `TrackEditRights` (`track_edit_rights(db, user)` once per request, then `.can_edit(track)`) is the single permission rule: platform admins, or admins of a club linked to the track's `sqorz_account_id` via `club_sqorz_accounts`; grant platform admin with `python -m app.auth.cli grant-admin <email>`. Changing `length_m` recomputes records for every athlete with laps on the track. Tracks are shared rows, so one edit shows for everyone who rode there. **Facility profile** (`training/facility.py`, `training/facilities.json`): sqorz calls every venue's full lap "Tour complet", so `Track.name` (what everything displays and sorts by) is the hand-set name once `name_is_custom`, else `Track.sqorz_name` (refreshed by every sync). The velodromes live in `facilities.json`, one entry per sqorz *account* (name, city/region/country, lat/lon, `width_m`, `surface`, `bank_straight_deg`/`bank_curve_deg`, `notes`, plus length/indoor/elevation/temp), applied to every track of the account on each backend start (`python -m app.training.cli apply-facilities`, chained before uvicorn in both backend Dockerfiles; a bad file exits 1 and the backend doesn't start) and to a track the normalizer creates (`apply_known_profile`). Null in the file = leave the DB value; a value in the file wins over a track-settings edit at the next start; a changed length recomputes records. Tests patch `known_profiles` to `{}` (conftest autouse) because the real file names the LS-03407 fixture's account. Two tracks of one account still list as separate entries with the same name in pickers. Real fixture facts: `tests/fixtures/LS-03407.json` has two distinct tracks both named "Tour complet" (different sqorz ids), so a records board can show the same place name twice.

**Physics** (`app/analysis/physics.py` ↔ `frontend/src/features/tools/physics.ts`): one model written twice — air density, the power equation `P = (v·(½ρ·CdA·v² + Crr·m·g) + m_eff·a·v)/η`, steady speed (Cardano), `simulate` (fixed-step RK4 effort: a standing start rides at `DEFAULT_START_POWER_RATIO` × race power, force-capped, until race pace; returns finish/split times and average power), `power_for_time` (bisection) and gearing. Both are checked to 1e-9 against `shared/physics-test-vectors.json`, which `python -m tests.physics_vectors` (from `backend/`) generates from the Python side — a model change means editing both files and regenerating; the physics itself is hand-checked in `tests/test_physics.py`. The frontend Docker images copy `shared/` to `/shared` because `tsc -b` type-checks the test that imports it.

## Frontend architecture

**Design system**: all styling goes through semantic tokens in `src/theme/tokens.css` (`--color-*`, `--chart-*`, `--space-*`, `--radius-*`, `--text-*`), defined for both `data-theme="light"` (paper) and `"dark"` (night session) — never use raw `--apex-*` palette values in components, or dark mode breaks. Reusable components live in `src/components/ui/` (Radix-based Dialog/Menu/Tabs/Tooltip/Toast, DataTable, StatTile, form fields…) and chart helpers in `src/components/charts/` (`axisProps`/`gridProps`/`ChartTooltip`/`ChartFrame`). `var()` works in Recharts stroke/fill props but **not** in gradient `<stop>` colors — use flat `fill` + `fillOpacity`. **Velodrome diagram**: `features/training/VelodromeDiagram.tsx` renders geometry from the pure, unit-tested `velodromeGeometry.ts` — a clothoid-transition track model (s = 0 at mid home straight where P1 sits, s increasing counterclockwise on a y-down screen), loop placement (`placeLoops`: length_m or furthest checkpoint, `NNNm` names = remaining distance to finish, P1 anchoring), and collision-avoiding label layout. Change placement rules there, with tests, not in the component.

**i18n** (FR/EN): i18next with per-namespace TS resource files in `src/i18n/locales/{en,fr}/` — English is the source of truth, and each French file `satisfies LocaleNamespace<typeof en>` so missing/extra keys fail `tsc`; `t()` keys are type-checked too (`src/i18n/i18next.d.ts`). Register new namespaces in `src/i18n/locales/index.ts`. Format numbers/dates/lap times only via `useFormat()` (`src/i18n/format.ts`: French uses a decimal comma, and `parseLocalDate` avoids the UTC off-by-one-day bug for `YYYY-MM-DD` strings). Request errors go through `errorMessage()` (`src/api/errors.ts`), mapping known HTTP statuses to translated text. The dev-only `/styleguide` route shows every component in both themes. The dev frontend container reinstalls npm deps on start (anonymous `node_modules` volume), so a new dependency just needs `docker compose restart frontend`.

**Tools** (`/tools/{power,pursuit,gearing,air}`, `features/tools/`): calculators over `physics.ts`. Every input lives in the URL query string (`toolInputs.ts`: param names, bounds, fallbacks; raw text kept as typed) so a link reproduces the screen, and `useToolInputs` fills what the URL lacks from the active athlete's current weight and a track (`length_m`/`elevation_m`/`default_temp_c`); "Copy link" writes every value in effect. Tabs keep the query string, so the tools share one setup. `/tools/pursuit/board` is registered outside `AppShell` (full-screen trackside board; `pursuitBoard.ts` reducer: start at the gun, tap per pursuit line, gap vs schedule). Pure helpers: `whatIf.ts`, `pursuitSchedule.ts`, `gearing.ts`.

**Clubs, coaching & "viewing as"** (frontend): `features/athletes/viewing.ts` holds whose data is shown when it isn't the user's own (per-tab sessionStorage, cleared on logout) and `useActiveAthlete()` returns that athlete — falling back to the user's own if access is lost — so every page must read its athlete through it, never `useMyAthlete`; `components/shell/AthleteSwitcher` + `ViewingBanner` are the UI, fed by the pure `buildSwitchOptions` (me, active coach links, rosters of clubs I administer). Routes: `/club` (list, create, paste an invite), `/club/:id/{members,athletes,invites,tracks,settings}` (tabs per role in `clubs/sections.ts`), `/join#token=…` (`JoinPage`; `ProtectedRoute` keeps path+search+hash in `state.from` so a signed-out invitee returns to the invitation after login/signup — Login/Signup pass it along), `/coach` ("Waiting for you" = link requests + unread comment threads, dashboard cards from `/coach-links/dashboard`, "My coaches"). The Coaching nav item's badge is `useCoachingBadgeCount`. Session comments live in `features/comments` (fifth tab of the session page; showing the thread marks it read). i18n namespaces `club` and `coach`. A bare `form { display: flex; flex-direction: column }` in `index.css` applies to every `<form>`, so a row layout needs an explicit `flex-direction: row`.

**Aero lab** (frontend; `features/aero/`, route `AeroPage` `/aero`, i18n namespace `aero`): session picker = sessions with a linked powered recording (`sessionsWithPower`), `?session=`/`?track=`/`?test=` (the saved test being edited) in the URL, the session page links to it when a recording has power. The estimate is a cached `useQuery` over the compute-only POST (`keepPreviousData`; assumption inputs debounced 400 ms via `hooks/useDebouncedValue`). Lap selection is `null` (automatic pick) until a lap is ticked (`toggleLap` starts from the used laps). The comparison card's "worth" is `aero.ts::worthSeconds` — `simulate` with the baseline's mass/air/Crr and only CdA changed. Pure helpers in `aero.ts` (tested).

Vite + React 19 + TypeScript, feature-folder structure under `src/features/<domain>/` (`api.ts`, `types.ts`, `use<Domain>.ts` hooks using TanStack Query), with route components in `src/routes/`. `src/api/client.ts::apiFetch` is the sole fetch wrapper — it handles the cookie-based auth refresh dance described above; new API calls should go through it rather than raw `fetch`. Routing (`src/App.tsx`) gates everything except `/login` and `/signup` behind `ProtectedRoute`, wrapped in the `AppShell` layout. Every page is `React.lazy` (the `Suspense` boundary is around the `Outlet` in `AppShell`, so the chrome stays put; the full-screen pursuit board has its own), and TanStack Query's default `staleTime` is 60 s — a mutation must invalidate the keys it changes, a remount no longer refetches for it.
